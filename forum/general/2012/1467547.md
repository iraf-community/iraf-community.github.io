<div>
I am trying to merely subtract a bias from a long list of image (about 450) and I'm getting strange errors.<br>
<br>
I've been able to reproduce them using dev$pix.<br>
<br>
Create a bunch of test files (for example 510) using<br>
<br>
<pre><code>!seq -f &#x27;imcopy dev$pix test%02g.fits&#x27; 1 510 &gt; script.cl
cl &lt; script.cl
!seq -f &#x27;test%02g.fits&#x27; 1 510 &gt; tlist
!seq -f &#x27;out%02g.fits&#x27; 1 510 &gt; olist
imcopy dev$pix bias.fits
imarith @tlist - bias.fits @olist</code></pre><br>
<br>
The last imarith command results (for me) in<br>
<br>
<pre><code>ERROR: Wrong number of elements in the operand lists</code></pre><br>
<br>
A shorter lists appear to run correctly. For these images, the 87 images or more (at least for my machine) produces the "wrong number of elements" error message.<br>
<br>
But some numbers of images less than 87 (for example 86) give a different error message:<br>
<br>
<pre><code>!seq -f &#x27;imcopy dev$pix test%02g.fits&#x27; 1 86 &gt; script.cl
cl &lt; script.cl
!seq -f &#x27;test%02g.fits&#x27; 1 86 &gt; tlist

imcopy dev$pix bias.fits
imarith @tlist - bias.fits @olist</code></pre><br>
<br>
results in<br>
<br>
<pre><code>tes is not an image or a number</code></pre><br>
<br>
The "tes" part is a truncated part of the file names.<br>
<br>
The exactly boundaries where this happens (like 86 or 256 for the original files where I noticed it) changes depending on the size of the images involved, so this might be some sort of out of memory error although my machine has 3GB of memory and should certainly be able to load 85'ish half-meg files based on dev$pix even if a few temporary files are involved for each. If this is being causes by out-of-memory conditions, the errors reported are unintuitive and I would think the design of imarith would makes it memory efficient so that all the images don't have to be loaded simultaneously.<br>
<br>
Can't figure this one out.<br>
