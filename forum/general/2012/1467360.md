**Mike Fitzpatrick** wrote on May 23, 2012

{% raw %}
<div>
I can confirm this is still present in the latest v2.16 system, but only on 32-bit linux systems.  It appears to be some sort of round-off problem in the converter code, i.e. if the test value is 1.0, or 5.0, or 2.0 then the last character will be different.  A '/' char comes immediately before a '0' in ascii but the converter isn't constraining the result. <br>
<br>
I'll fix this for the next update, the workaround for now is to specify some level of precision, e.g. "%.8f"
</div>
{% endraw %}
