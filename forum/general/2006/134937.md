# Possible copy bug

**Jason Quinn** wrote on Apr 30, 2006

{% raw %}
<div>
I may have found a bug in IRAF's <em>copy</em> command. I've noticed that <em>copy</em> corrupts some gzipped files. For instance, try downloading and <em>copy</em>'ing <strong>table.2.gz</strong> from<br>
<br>
<a href="http://vizier.cfa.harvard.edu/viz-bin/ftp-index?/ftp/cats/J/A%2bA/424/919/x70z02">http://vizier.cfa.harvard.edu/viz-bin/ftp-index?/ftp/cats/J/A%2bA/424/919/x70z02</a><br>
<br>
Notice the file size increases by 1 after a copy. The UNIX <em>cp</em> command does not corrupt the file allowing <em>gunzip</em> to run without a premature end of file error. Some of the other files from the URL such as <strong>table.10.gz</strong> and <strong>table.16.gz</strong> exhibit the same behavior. Ideas?<br>
<br>
Jason
</div>
{% endraw %}

**Mike Fitzpatrick** wrote on Apr 30, 2006

{% raw %}
<div>
This is a side-effect of the size of an SPP character (two bytes) meaning that iraf file i/o can't write an odd number of bytes to a file.  In most cases the extra NULL is harmless but this is one case where a host program doesn't like it (another being some tasks reading the GIF images produced by EXPORT, however there a "null extension" is actually in the gif spec but rarely implemented as legal).  <br>
<br>
Changing the size of an spp char is a one-line change, but after 20 years there may be untold numbers of unintended consequences in other tasks.  OTOH, we're in good shape to start using unicode chars in the system 8-)  Simplest thing is to just use 'cp' for binary files, it's a default foreign task and is readily available.<br>
<br>
-Mike<br>
<br>
P.S. Note: This isn't a file corruption of any kind, it is just that there is an extra NULL byte on the file in the event the input file was an odd size.
</div>
{% endraw %}
