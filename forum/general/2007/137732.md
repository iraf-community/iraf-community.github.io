<div>
From an earlier reply to a similar problem:<br>
<br>
<blockquote><br>
As you already know, allstar needs the header parameter FUNCTION, from<br>
the psf image, to fit the psf for all other stars.  This parameter is<br>
written when you run the psf task, which gets the FUNCTION parameter<br>
from 'daopars'.<br>
<br>
If you take a look at the psf header, you should find parameters such<br>
as PSFX, PSFY, PSFHEIGHT, and PSFMAG.  These are accompanied by the<br>
FUNCTION parameter.<br>
<br>
If the FUNCTION parameter is missing, you should check that you have the<br>
function type set in 'daopars' (see 'phelp daopars' for a list of<br>
available functions).  Also be sure that 'update' is set to 'yes' in the<br>
daophot parameters (epar daophot).<br>
</blockquote><br>
<br>
Write back if you still have problems.<br>
<br>
-Mike

**Mike Fitzpatrick** wrote on Jul 10, 2007

{% raw %}
<div>
If you mean the long IMHEADER output contains a line such as:<br>
<br>
<pre><code> Pixel file &quot;/tmp/foo.pix&quot; [NO PIXEL FILE]</code></pre><br>
<br>
then it means the pixel file associated with the .imh can't be found.  This can happen when you move imh images between machines and forget to copy the .pix files, have an invalid 'imdir' so it couldn't be created, or the directory doesn't exist.  You can HEDIT the 'i_pixfile' header parameter to reset this pathname and reconnect to the .pix file, otherwise check that your 'imdir' directory exists and you can write to it (the value is set in login.cl).<br>
<br>
Updating/reading of headers should still be allowed,  but sometimes errors cascade from some underlying reason like this and so may be bogus.  Try fixing the pixel file problem first.<br>
<br>
Cheers,<br>
-Mike
</div>
{% endraw %}
