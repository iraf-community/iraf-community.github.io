# memory corruption in xyxymatch

**gelato** wrote on Jul 05, 2010

{% raw %}
<div>
A colleague has stumbled upon a bug in xyxymatch. When nrefstars==3, nrmaxtri (which is used in computing the allocation size for reftri) ends up being equal to 1. Later, rg_tvote() (called via rg_match()) assigns values to reftri(2,RG_MATCH) and reftri(3,RG_MATCH) which are out of bounds.<br>
<br>
I suggest the following changes to the code:<br>
<br>
[list=1:473cb7fdde]<br>
<li> in pkg/images/immatch/src/listmatch/t_xyxymatch.x add a line<br>
<pre><code>
      nrmaxtri = max (nrefstars, nrmaxtri)
</code></pre><br>
before calling calloc(reftri, ...). A similar change is almost certainly required in pkg/images/imcoords/src/t_ccxymatch.x . Also, the computed value for ninmaxtri may need to be adjusted by<br>
<pre><code>
      ninmaxtri = max (nliststars, nrefstars, ninmaxtri)
</code></pre><br>
<li> in pkg/images/lib/rgmerge.x, document the requirement that nrmtri&gt;=nrefstars in rg_tvote().<br>
<li> also in pkg/images/lib/rgmerge.x, correct the definition of rg_factorial() to conform with the documentation: there is a hardcoded 3 which should really be ngroup. It doesn't matter to t_xyxymatch() which calls rg_factorial with ngroup==3, but it isn't right.<br>
</ul>
</div>
{% endraw %}
