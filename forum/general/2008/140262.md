# Bug in imcombine sigclip task?

**jhaislip** wrote on Oct 02, 2008

{% raw %}
<div>
noao&gt;imred&gt;ccdred<br>
source located in immatch<br>
<br>
combine = average<br>
reject = sigclip<br>
nkeep = 1<br>
mclip = yes  (use median as reference value)<br>
lsigma = 1.0<br>
hsigma = 1.0 <br>
<br>
All other params default.<br>
<br>
To illustrate the possible bug, combine the following 10 pixels with the settings above.<br>
<br>
[0,1,12,23,24,24.5,26,37,38,39]<br>
<br>
Iraf's result is 23.8333.<br>
<br>
Manually, you can check the algorithm as follows:<br>
<br>
Iteration 1:<br>
The median value is 24.25 and the standard deviation (using median) is 14.35. After clipping, we are left with:<br>
<br>
[12,23,24,24.5,26,37,38]<br>
<br>
Iteration 2:<br>
The new median is 24.5 and the new standard deviation is 9.12.  After clipping we are left with:<br>
<br>
[23,24,24.5,26]<br>
<br>
Iteration 3:<br>
The new median is 24.25 and the new standard deviation is 1.26.  After rejection we are left with:<br>
<br>
[23,24,24.5]<br>
<br>
Iteration 4:<br>
The new median is 24.0 and the new standard deviation is 0.79.  After rejection we are left with:<br>
<br>
[24,24.5]<br>
<br>
Rejection is complete and, therefore, the resulting combined pixel value is 24.25.<br>
<br>
Why does the IRAF result not agree?  IRAF's result comes from the average of 23,24, and 24.5.  So IRAF is not rejecting 23.  I have tracked this issue down in the source code to 'as.pcix/pkg/images/immatch/src/imcombine/src/icsclip.gx' on line 405. The lower threshold rejection FOR loop terminates if the number of lower threshold rejected pixels is greater or equal to the number of remaining pixels. When we reach iteration 3 we have rejected 3 pixels due to the lower threshold and the number of pixels remaining is 3, therefore the FOR loops immediately terminates.  This prevents IRAF from rejecting the '23' pixel.  <br>
<br>
I have generated an image from IRAF using these parameters and also generated an image using the same parameters from my own sigma clipping algorithm.  Comparing the result shows that all of IRAF's pixels are &lt;= all of my pixels.  The problem I have noted above would explain this difference.  By stopping the lower sigma rejection FOR loop prematurely, you are not rejecting as many low pixels as you should be rejecting.  This will have an overall effect of lowering the pixel counts -- which is what we see. <br>
<br>
Can anyone help my understand IRAF's behavior?  Or have I just made a mistake in my algorithm?<br>
<br>
Thanks!<br>
<br>
Joshua Haislip
