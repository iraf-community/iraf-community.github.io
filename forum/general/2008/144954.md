# data type changes and fits header definitions II

**rclark** wrote on Nov 26, 2008

{% raw %}
<div>
An image file is being created with the statement:<br>
<br>
op = immap (Memc[outname], NEW_COPY, ip)<br>
<br>
so existing header information will be copied, as only a small number of<br>
keywords are to be changed. However among the changes is the data type of<br>
image array. These can include changes of data type and array sizes (the<br>
complex data type was being used in some places-- we're trying to get away<br>
from this for file io) as reflected in IM_PIXTYPE[op], IM_NDIM[op], and<br>
the dimension sizes in IM_LEN[op,n]. (defined in inhdr.h)<br>
<br>
The code I'm looking at, and needing to modify, also calculates<br>
IM_BUFSIZE. (defined in imset.h)<br>
<br>
bufsize = npix*sizeof(IM_PIXTYPE(op))<br>
call imseti (op, IM_BUFSIZE, bufsize)<br>
<br>
So my question is...<br>
How are these IM_* values communicated to the fits kernal?<br>
Is it necessary (or desireable) for the user to be messing around with<br>
this bufsize value? And if so, is it necessary to explicitly set it<br>
with an imseti call? There are no corresponding calls for the IM_NDIM,<br>
IM_LEN and IM_PIXTYPE values in the code. Multiple files undergoing the<br>
same type of processing are open simultaneously.<br>
<br>
And finally there will be a line like:<br>
<br>
call amovr(Memr[data], Memr[imps3r(op, 1,2, 1,ncols, 1,nlines)], npix)<br>
<br>
where the data type of the vos or Mem reference will need to be<br>
changed.<br>
<br>
Are there any tools to help check type consistency here. (you're<br>
welcome to place bets on whether I'll miss a few. I know which way<br>
I'm betting:-)<br>
<br>
In older versions of iraf there was a tool called spplint. Might it be<br>
able to help with this? and whatever became of it?
</div>
{% endraw %}

<div>
You can ignore the IM_BUFSIZE thing, it is only a way to optimize the file i/o buffer size.<br>
<br>
<blockquote><br>
And finally there will be a line like:<br>
<br>
call amovr(Memr[data], Memr[imps3r(op, 1,2, 1,ncols, 1,nlines)], npix)<br>
<br>
where the data type of the vos or Mem reference will need to be<br>
changed.</blockquote><br>
<br>
If you want to change the types, look at the achtXY() functions in the sys$osb directory to e.g. convert real to int for a vector.  Not that something like imps3r() returns a pointer to real which must match the Mem array being used (this is an alignment issue, you won't get a compile-time error so it's a silent bug you'll pull your hair out over for days).<br>
<br>

welcome to place bets on whether I'll miss a few. I know which way<br>

<br>

</blockquote><br>
<br>
This was actually a host command written for Sun systems that was never fully ported to PC-IRAF platforms.  It mostly used GCC error messages which you get for free now so there was no urgency.   It did however use prototypes that might help, but I haven't got a version to give you that works.<br>
