# hsel non-graceful handles invalid string as keyword

**Jason Quinn** wrote on May 24, 2008

{% raw %}
<div>
I ran across some images that have in their header<br>
<pre><code>FILTER  = &#x27;r&#x27;&#x27;                                     / FILTER NAME</code></pre><br>
which violates the FITS 2.0 standard with its quoting and causes <strong>hsel</strong> to freak out. I think it would be valuable if hedit did a basic check on the formatting of strings in keywords. It could then either throw an error or try to work around problems. For instance, in this case, it might be a good idea to default to the maximum size string defined by the first and last single quote. <br>
<br>

<div>
Hi Jason,<br>
<br>
This particular keyword violates the standard on two separate counts (i.e. the embedded quote and the string not terminating before column 20).  The problem however is farther down in the image i/o routines getting the header keyword before HSELECT even sees it so the fix is a little more subtle than you suggest.<br>
<br>
I can add this to the list of future fixes, for now you might just want to use HFIX to fix the keyword value and send a nasty email to the author of the code that write the file.  For example,<br>
<br>
<pre><code> hfix foo.fits command=&quot;!sed \&quot;s/&#x27;&#x27;/&#x27;&#x27;        &#x27;/g\&quot; $fname &gt; t;mv t $fname&quot;</code></pre><br>
<br>
should fix both issues, but be careful you get the quotes and escaped-quotes correct.<br>
<br>
Cheers,<br>
-Mike

I wanted it put into a UNIX-level script though. Here is the solution that I used the other day:<br>
<pre><code>
perl -pi -e &quot;s/FILTER  = \&#x27;(.)\&#x27;\&#x27;/FILTER  = \&#x27;\1\&#x27; /&quot; badfile.fits
</code></pre><br>
<br>
It seems like extended regex replacement from the command line on a <em>binary file</em> is currently a chink in Linux's armor. Despite several hours of searching, I only found two ways to tackle the problem at the UNIX level with command programs (<strong>vi</strong> and <strong>perl</strong>) and only one can be scripted (perl). There appears to be a number of good 3rd party binary regex replacement programs although I only would use them as a last resort. Unfortunately, GNU <strong>sed</strong> can do simple regex replaces for binary files with text but not <em>extended</em> regex replaces in that circumstance. Vi has a binary edit mode and you can do a regex search-n-replace; however this seems to only work properly from within the visual editor and fails if you try to pass it an extended regex from the command line like from within a script. Perl's command line version seems to work after getting the all-important quoting correct but I'm not convinced it does extended regexs properly from the command line either.<br>
