# Optimizer / IRAF dynamic memory conflict

**joequant** wrote on Oct 29, 2013

{% raw %}
<div>
<br>
                Just a heads up with a problem we found and fixed on linux.  It's a very subtle problem that causes random seeming bugs.<br>
<br>
https://bugs.mageia.org/show_bug.cgi?id=11507<br>
<br>
The basic issues is that IRAF dynamic memory works with memory that is out of bounds.  The problem here is that some loop optimizers will see that there is a loop operating with out of bounds memory and then optimize it with something undefined since according to the C standard, out of bounds behavior is undefined.<br>
<br>
This causes problems with f2c running with GCC 4.8.  We fixed it by forcing the f77.sh wrapper to run with -fno-aggressive-loop-optimization<br>
</div>
{% endraw %}

**joequant** wrote on Oct 30, 2013

{% raw %}
<div>
<br>
                Sorry if this is a duplicate....<br>
<br>
Yes the memory is properly allocated, however the trick has some unintended side effects.  What is happening is that fortran finds the base of the heap with an array of size one.  F2C converts this into a static structure of one element.  When gcc 4.8 does the static analysis it sees the memd pointer, sees that it is assigned to a static array of size one, and then assumes that any references to the array of greater than 1 are pointing to unallocated memory.<br>
<br>
If there were another way of getting a pointer to the base of the heap other than with an array of length one, this would be nice since it would mean that IRAF could be ported to F90.  The trick of using an array as a pointer works in f77 but its forbidden in f90, and I haven't been able to think of a workaround.<br>
<br>
Also, this was a nasty bug to track down because the compiler has the option to choose what code to generate, and usually it will generate the right code, but the optimizer will sometimes try to optimize out the loop.<br>
</div>
{% endraw %}

**joequant** wrote on Nov 01, 2013

{% raw %}
<div>
<br>
                OK, I have some more information about the root causes and fix for the problem.<br>
<br>
The issue is that gcc 4.8 is extremely aggressive at using SSE2 instructions to deal with double arithmetic.  However for these instructions to work, the doubles have to be aligned on 128-bit memory addresses.  This does not have to do with 32/64-bit.<br>
<br>
The compiler issues were because the IRAF memory management caused a situation in which gcc assumed that the memory was 128-bit aligned but it was not in fact aligned, so the SSE2 instructions were causing failures.<br>
<br>
The fix is to change IRAF memory management to force alignment on 128-bit addresses.  The two changes are <br>
<br>
1) Change config.h to<br>
<br>
define  SZ_MEMALIGN     (2*SZ_DOUBLE)   # alignment criteria for malloc<br>
<br>
2) change f77.sh to include<br>
<br>
                sed -i -e "s/memd\[1\]/memd\[2\]/" $b.c<br>
<br>
Without this change, the compiler may not align memd against a 128-bit boundary.  By having two doubles, gcc 4.8 does the initial alignment correctly<br>
<br>
</div>
{% endraw %}

                This is also reported as <a href="https://github.com/iraf/iraf-v216/issue/73">issue #73</a> of IRAFs github repository. This is a major problem, as it may lead to <strong>wrong results</strong>, if a user compiles his own code. <br>
<br>
To bring a specific example here (taken from the <a href="https://github.com/olebole/iraf-v216/blob/ba52ab58fd81b9bff6f421239ee444513fef9ded/test/programming.md#loop-optimization">test suite</a>), and performed with the original 2.16.1 binary distribution:<br>
<br>
Take the following task as <strong>otest.x</strong>:<br>
<br>
SPP Formatted Codetask otest = t_otest<br>
<br>
procedure t_otest ()<br>
<br>
int i<br>
<br>
pointer p, sp<br>
<br>
begin<br>
<br>
    call smark(sp)<br>
<br>
    call salloc(p, 4, TY_DOUBLE)<br>
<br>
    do i = 1, 4<br>
<br>

    }<br>

    call sfree(sp)<br>

end<br>
