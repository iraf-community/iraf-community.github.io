	Also, check that you've got a /usr/local/lib/imtoolrc symlink<br>
(pointing to iraf$dev/imtoolrc) on your system.  If missing then DS9<br>
may be falling back to some default since it doesn't know then what an<br>
'imt2048' is.  You can also copy dev$imtoolrc to ".imtoolrc" in your unix<br>
login directory if you can't write to system dirs.<br>
<br>

&gt; This is an inherent limitation of IRAF in the way it interphases with  <br>
&gt; the image display as it uses the fifos to pass the info on each  <br>
&gt; pixels (X,Y, and pixel value). However the astrometry information is  <br>
&gt; stored in the header of the fits file and this is not sent by IRAF to  <br>
&gt; DS9 (or SAOimage or XImtool). I suspect that this happens for  <br>
&gt; historic reasons. In the past IRAF could not display fits files, and  <br>

&gt; May be then it was programatically difficult to send the WCS info  <br>

<br>
	Actually, this is a limitation in DS9.  Since the V2.11.3 days<br>
(about 6 years ago) the display protocol will pass in additional wcs<br>
info that includes a fully qualified path to the file.  In XImtool this<br>
info is used by an external task (which knows how to read the image/WCS)<br>
to map display cursor positions to real-pixel/WCS values in the display.<br>
Given the filename DS9 could do something similar to read the WCS from <br>
the image and provide the same capability.  I know they actually get this<br>
information since they used the IIS display protocol code written for<br>
ximtool verbatim, they just don't use it.  It wouldn't matter if we sent<br>
the entire header, DS9 would still have to be changed to use it!  SAO has<br>
been aware of this for a while but just hasn't fixed it.<br>
