**Mike Fitzpatrick** wrote on Feb 24, 2006

{% raw %}
<div>
<blockquote>reset tables /iraf/extern/tables </blockquote><br>
<br>
Note that a trailing '/' is required on these paths, the same for stsdas.<br>
<br>
<blockquote>Then I change from root to IRAF user (I am still in the directory /iraf/extern/tables) <br>
su iraf <br>
setenv IRAFARCH suse <br>
source $iraf/unix/hlib/irafuser.csh <br>
</blockquote><br>
<br>
The preferred method is "su - iraf" so you effectively login as 'iraf'.  This will also pick up the $iraf defined in the iraf account .login file (assuming this was setup to use C-shell).<br>
<br>
<blockquote>After that I log on as root (in the same directory): <br>
ln -s bin.suse bin <br>
After that when I try (in /iraf/extern/tables): <br>
<br>
mkpkg suse <br>
<br>
I get the message: <br>
bash: mkpkg: command not found </blockquote><br>
<br>
The files should normally be owned by the iraf user, but it doesn't really matter.  What does matter is that you have the proper $iraf/$IRAFARCH et all defined in the environment before you try compiling.  If you log back in as root then you'll need to redefine these for the root user.  Resetting the package architecture is normally done with <br>
<br>
    mkpkg -p tables suse<br>
<br>
The 'command not  found' probably just means that /usr/local/bin (or wherever you installed the iraf commands) isn't in the path.  Don't forget the '-p tables' (and for STSDAS both '-p tables -p stsdas' flags so the package environment is loaded.  Existing redhat binaries for both packages are also likely to work so long as you install then in a 'bin.suse' directory.  Hope this helps.<br>
<br>
Cheers,<br>
-Mike
</div>
{% endraw %}
