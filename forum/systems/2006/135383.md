<blockquote>I realize I'm ahead of the game a bit, but is there a way (.e.,g., with XFLAGS<br>
or LFLAGS) to force XC to use a 32-bit compilation. </blockquote><br>
<br>
XC will accept the following environment flags to modify the compilation:<br>
<br>
XC_CFLAGS<br>
XC_FFLAGS<br>
XC_LFLAGS<br>
<br>
as well as XC_CC, XC_F77 and XC_LINKER to change the command used for each stage of the compilation or source file.  So, try <br>
<br>
    setenv XC_FFLAGS "-m32"<br>
<br>
to force 32-bit.  Note this may be a problem for the F2C driver script, I can send you a patched version if needed.  Put these definitions in your .cshrc file so they'll be picked up when MKPKG calls XC.<br>
<br>
<blockquote>What do you think the chances are of a successful sysgen on the 64-bit<br>
system?</blockquote><br>
<br>
About the same chance we'll get snow later today.  The IRAF kernel is not 64-bit clean and things like pointers, file descriptors, structures, etc all need to be looked at.  It is essentially a new platform port at this level.  Beyond that, applications need to be reviewed, e.g. the NPIX counter from IMSTAT needs to become a long integer, header structures may need to be changed, etc.  I can make it easier to force 32-bit compiles, full 64-bit support is a lot of repetative checking of code.<br>
<br>
BTW, on the Alpha we got away with using the '-taso' flag when compiling<br>
and at the time GCC didn't have a -m32, one reason we couldn't ever do an Alpha/linux port.  Linux kernels are already starting to mess with the memory model we rely on internally, at some point this will become much more critical.<br>
<br>
In case you're wondering:  It is cloudy now but a little warm.....<br>

Cheers,<br>
-Mike
