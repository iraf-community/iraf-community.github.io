<div>
Hi James,<br>
<br>
Which package is this and what file is failing to compile?  For the most part the &lt;iraf.h&gt; is needed only when compiling the IRAF kernel and things like the CL/ECL or LIBC.  For applications, the usual need is to define the '-Inolibc' and '-H' flags to compile a C host program.  These flags are usually added in the package mkpkg file rather than system-wide, note you would modify the XFLAGS (not CFLAGS) since XC should be used to compile even .c sources.  Lastly, if you need to pass a flag through to the host compilers (e.g. '-foo') and don't want XC to try to interpret it, the trick is to pass is a '-/foo' where the '/' acts as an escape.<br>
<br>

<blockquote>Can you think of any way to avoid that without recompiling IRAF itself? </blockquote><br>
<br>
Define $iraf in your environment.  The other paths this file supplies are $tmp (i.e. /tmp/) and $host (i.e. $iraf/unix/), otherwise it is used when building the iraf kernel or anytime iraf networking in invoked (i.e. the 'node!').  For iraf networking, the /usr/include location is hardwired unless you rebuild the system.<br>

**Mike Fitzpatrick** wrote on Jul 23, 2008

{% raw %}
<div>
The location of the &lt;iraf.h&gt; file is not platform dependent, the only reason it would work on PPC but not macintel is if the IRAFARCH were set incorrectly or the hlib$mkpkg.inc file put it in the wrong place.  In v2.15 an alternative for /usr/include is $HOME/.iraf which is defined globally, otherwise you need the XFLAGS (or XC_XFLAGS environment variable) to add the -I flag to the underlying compiler flags.   Note you can also put the XFLAGS on the commandline, e.g.<br>
<br>
<pre><code>mkpkg XFLAGS=&#x27;-/I/opt/include&#x27;</code></pre><br>
<br>
What path are you trying to use and how is it being set?
</div>

**Mike Fitzpatrick** wrote on Jul 23, 2008

{% raw %}
<div>
<blockquote>The iraf.h link is located in /my/path/to/include/ and points to /my/path/to/iraf/iraf/unix/hlib/libc/iraf.h. </blockquote><br>
<br>
Unless you are compiling the iraf kernel (or some select C interfaces), this file is only used by applications to get the $iraf, $tmp and $host paths,  You can always just define $iraf and $tmp in your .cshrc environment to avoid the error message and path problem.<br>
<br>
<blockquote><br>
My IRAFARCH is set to macintel, which I believe is correct (uname -m = i368).</blockquote><br>
<br>
For pre-v2.15 systems only.  In v2.15 the 32-bit intel binary is now part of the 'macosx' universal (ppc+intel) architecture and 'macintel' refers to 64-bit Intel only. <br>
<br>
<blockquote><br>
In v2.15, how do you globally define $HOME/.iraf as an alternative to /usr/include? <br>
</blockquote><br>
<br>
It is defined in the hlib$irafuser.csh file, but only for the iraf kernel flags.  Since I doubt you're building the system from source you normally wouldn't need this file for applications code, and at runtime its used for getting the $iraf root dir if it isn't found in the environment.  Note that certain external packages shouldn't be linked against v2.15 since they haven't been ported to 64-bit yet (although a build on 32-bit systems would probably work fine).
</div>
