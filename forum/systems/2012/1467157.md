# reading fits files with 64 bit SPP

**rclark** wrote on Jan 31, 2012

{% raw %}
<div>
I am having problems accessing a fits file in an application written in<br>
SPP when it is compiled with a 64 bit installation of iraf v215.<br>
<br>
The file has dimension [900,1024,6].<br>
The BITPIX value is 32.<br>
<br>
The existing version compiled with v213 and copied to the 64 bit platform<br>
 works fine.<br>
<br>
The problem is that pixels are not being addressed correctly in the<br>
64 bit version. For instance referencing [451,1,1] goes to [1,2,1].<br>
<br>
So I stripped it down and wrote just a pixel reader.<br>
I immap the file, read the whole image with imgs3r and then select<br>
specific pixel column, row, plane to check.<br>
<br>
I address the pixel by multiple methods:<br>
<br>
* Explicitly calculate the offset and read directly from the Memr[].<br>
<br>
* Pass Memr[array pointer] to another procedure where it is declared<br>
as a multidimension array and referenced in the normal way.<br>
<br>
* calculate the offset and copy the specific plane into another MALLOCed<br>
array which I again read both with an explicit offset and in a subroutine<br>
as a 2d array.<br>
<br>
All 4 methods are consistant with each other and return the same value.<br>
When I compare the 32 and 64 bit versions I get different results. The<br>
32 bit version gives the correct result (verified by reading and<br>
examining the image with ds9).<br>
<br>
The 64 bit version gives the correct results for the first half of the<br>
first row of the first plane. That is, pixels [1:450,1,1] are read<br>
correctly. But beginning with [451,1,1] an incorrect pixel is accessed.<br>
<br>
64 bit location -&gt; mapped to (correct) 32 bit location<br>
[451,1,1] -&gt; [1,2,1]<br>
[452,1,1] -&gt; [2,2,1]<br>
...<br>
[1,2,1] -&gt; [1,3,1]<br>
etc.<br>
<br>
Starting at plane 1, row 513 it starts mapping onto the 2nd plane.<br>
cols 451:900 don't seem to be addressable. At least I haven't found<br>
where they get mapped to. Starting at plane 4 it starts getting into<br>
what looks like a 0 filled area. I haven't invested any time exploring<br>
up there.<br>
<br>
Has anyone else seen this behavior? At first glance this doesn't look<br>
quite like the sort of issue that P2R addresses.<br>
<br>
It seems like the issue is with fits io procedures. The way the array is<br>
dimensioned should be completely indepent of the Memr mechanism so 450<br>
(900/2) should not be any sort of magic number. But imgs3r does have the<br>
dimension values passed to it.<br>
<br>
I haven't tried accessing subsections of the image in the imgs3r call<br>
or trying to trick it with bogus dimensions.<br>
<br>
Thanks for any pointers that could help with this.<br>
<br>
Richard<br>
<br>
The relevant code snippets follow:<br>
<br>
pointer immap(), imgs3r()<br>
pointer ioimg, pxbuf, pxpl<br>
real    pixval<br>
...<br>
ioimg=immap(fnam,READ_ONLY,0)<br>
nax = imgeti(ioimg,"i_naxis")           # dimensions and offsets<br>
nax1 = imgeti(ioimg,"i_naxis1")<br>
nax2 = imgeti(ioimg,"i_naxis2")<br>
nax3 = imgeti(ioimg,"i_naxis3")<br>
pxbuf = imgs3r(ioimg, 1,nax1,1,nax2,1,nax3)<br>
plsize = nax1 * nax2<br>
size = plsize * nax3<br>
call malloc(pxpl, plsize, TY_REAL)<br>
...<br>
offset = (ipl-1)*plsize + (irow-1)*nax1 + icol-1<br>
pixval=Memr[pxbuf+offset]<br>
# some printf statements...<br>
<br>
call amovr(Memr[pxbuf+(ipl-1)*plsize],Memr[pxpl],plsize)<br>
offset = (irow-1)*nax1 + icol-1<br>
pixval=Memr[pxpl+offset]<br>
# some printf statements...<br>
<br>
# a bunch of printf statements are in the arr subroutines.<br>
call arr3d(Memr[pxbuf], nax1,nax2,nax3, icol,irow,ipl)<br>
call arr2d(Memr[pxpl], nax1,nax2, icol,irow)<br>
...
