From: fitz@tucana.tuc.noao.edu (Mike Fitzpatrick)
Newsgroups: adass.iraf.system
Subject: CL Arrow-Key History Translations
Date: 5 Dec 2000 00:12:38 -0700
Organization: IRAF Project, National Optical Astronomy Observatories


	One of the most common CL-feature requests is the ability to use
the arrow keys to scroll through the CL history in the same way as is done
with tcsh shells.  This was implemented directly in the NCL as part of
the SAO R&amp;D package (http://hea-www.harvard.edu/RD) by Eric Mandel, but
it turns out this can largely be done using the existing translations
provided by Xterm and XGterm without modifying the CL at all.

	The idea is to use the keymap() translation function to program
various keymap &quot;modes&quot; for the window, each mode can redefine the action
taken by certain keys to provide extra keyboard functionality for a given
task.  In this case we can define a &quot;CL mode&quot; which remaps the arrow keys
to implement the arrow-key history mechanism by invoking EHISTORY automat-
ically.  As it turns out other modes and translations are needed so the
arrow keys still work as expected when in EPAR and so modes terminate
correctly.  

	The translations are appended to this posting.  To use them do
the following:

    1) Save the translations to your .Xdefaults file (or whichever file
       defines your user resources).
    2) Load the new resources using the command

		% xrdb -load ~/.Xdefaults

       and start a new XGterm.
    3) In the new window, log into the CL and type various commands to
       establish a history list.
    4) To begin using the arrow keys, type the F2 key to begin CL mode,
       the arrow keys can then be used as in tcsh to scroll through the
       history.
    5) If a problem occurs (i.e. arrows no longer work as expected), or
       you leave the CL, type F1 to reset to the default keymap mode.
    6) Aside from the arrow keys these translations also redefine the
       following function keys in CL mode 
		F2	toggle the graphics window
		F3 	invoke the graphics cursor
		F4	invoke the image cursor
    7) An example mode for remapping the arrows for use with DBX is also
       shown, this is invoked with the F3 key from the normal mode.


LIMITATIONS:
   - Because these translations affect the text window all the time leaving
     the keymap in CL mode will cause the arrow keys to be remapped even
     when you&#x27;re not still in the CL.  This means that e.g. the arrows
     will no longer scroll the history in the normal unix tcsh.  The F1 key
     will reset to the default mode in all cases.
   - Occassionally you can be left in the ehist mode is you scroll off
     the top of the CL history stack, again use F1 to reset.
   - The translations here are for use with the &#x27;vi&#x27; editor, emacs users
     should consult the dev$emacs.ed file for a listing of the keys necessary
     for movement with that editor.
   -  Care should be taken to select keyboard function keys that don&#x27;t
     overlap with functions mapped to them by the window manager (e.g F5 may
     be used by the WM to iconify the window and overrides it&#x27;s use as a
     translation here).  Modifiers such as Shift, Ctrl or Alt can be used to
     work around this.

While not perfect these translations seem to work in most cases.  They&#x27;re
provided &quot;as is&quot; and it&#x27;s hoped people will follow-up with other more clever
translations or fixes.  For more details on translation functions available
see the xterm man page.


-Mike

*VT100.Translations: #override \
    !&lt;Key&gt;F1: 		keymap(None)				\n\
    !&lt;Key&gt;F2: 		keymap(cl)				\n\
    !&lt;Key&gt;F3: 		keymap(dbx)

*VT100.clKeymap.translations: #override \
    !&lt;Key&gt;F1: 		keymap(None)				\n\
    !&lt;Key&gt;F2: 		set-visibility(tek,toggle)		\n\
    !&lt;Key&gt;F3: 		string(&quot;=gcur\n&quot;)			\n\
    !&lt;Key&gt;F4: 		string(&quot;=imcur\n&quot;)			\n\
    !&lt;Key&gt;e: 		keymap(epar)  string(&quot;e&quot;)		\n\
    !&lt;Key&gt;Up: 		keymap(ehist) string(&quot;ehist\n&quot;)		\n\
    !&lt;Key&gt;KP_Up: 	keymap(ehist) string(&quot;ehist\n&quot;)		\n\
    None&lt;Key&gt;Down: 	string(0x0A) keymap(epar)		\n\
    None&lt;Key&gt;KP_Down: 	string(0x0A) keymap(epar)

*VT100.ehistKeymap.translations: #override \
    &lt;Key&gt;Return:	string(0x0D) keymap(cl)			\n\
    &lt;Key&gt;e: 		string(&quot;e&quot;)  keymap(ehist)		\n\
    &lt;Ctrl&gt;c:		string(0x0D) keymap(cl) string(0x03) 	\n\
    &lt;Ctrl&gt;u: 		string(0x0D) keymap(cl) string(0x15)	\n\
    None&lt;Key&gt;Up: 	string(0x0B) keymap(ehist)		\n\
    None&lt;Key&gt;KP_Up: 	string(0x0B) keymap(ehist)		\n\
    None&lt;Key&gt;Down: 	string(0x0A) keymap(ehist)		\n\
    None&lt;Key&gt;KP_Down: 	string(0x0A) keymap(ehist)		\n\
    None&lt;Key&gt;Left: 	string(0x08) keymap(ehist)		\n\
    None&lt;Key&gt;KP_Left: 	string(0x08) keymap(ehist)		\n\
    None&lt;Key&gt;Right: 	string(0x0C) keymap(ehist)		\n\
    None&lt;Key&gt;KP_Right: 	string(0x0C) keymap(ehist)		\n\
    !Alt&lt;Key&gt;Left: 	string(0x02) keymap(ehist)		\n\
    !Alt&lt;Key&gt;KP_Left: 	string(0x02) keymap(ehist)		\n\
    !Alt&lt;Key&gt;Right: 	string(0x17) keymap(ehist)		\n\
    !Alt&lt;Key&gt;KP_Right:	string(0x17) keymap(ehist)

*VT100.sectionKeymap.translations: #override \
    !&lt;Key&gt;Return:	string(0x0D) keymap(epar)		\n\
    !&lt;Key&gt;colon: 	string(0x3A) keymap(epar) 		\n\
    &lt;Key&gt;bracketright:  string(0x5D) keymap(epar)

*VT100.eparKeymap.translations: #override \
    !&lt;Key&gt;Return:	string(0x0D) keymap(cl)			\n\
    !&lt;Key&gt;colon: 	string(0x3A) keymap(cl) 		\n\
    &lt;Key&gt;e: 		string(&quot;e&quot;)  keymap(epar)		\n\
    None&lt;Key&gt;Up: 	string(0x0B) keymap(epar)		\n\
    None&lt;Key&gt;Down: 	string(0x0A) keymap(epar)		\n\
    None&lt;Key&gt;KP_Up: 	string(0x0B) keymap(epar)		\n\
    None&lt;Key&gt;KP_Down: 	string(0x0A) keymap(epar)		\n\
    !Alt&lt;Key&gt;Left: 	string(0x02) keymap(epar)		\n\
    !Alt&lt;Key&gt;KP_Left: 	string(0x02) keymap(epar)		\n\
    !Alt&lt;Key&gt;Right: 	string(0x17) keymap(epar)		\n\
    !Alt&lt;Key&gt;KP_Right:	string(0x17) keymap(epar)		\n\
    &lt;Key&gt;bracketleft: 	string(0x5B) keymap(section)

*VT100.dbxKeymap.translations: \
    !&lt;Key&gt;F1: keymap(None) \n\
    None&lt;Key&gt;Right: 	string(&quot;next\n&quot;) 			\n\
    None&lt;Key&gt;Down: 	string(&quot;step\n&quot;) 			\n\
    None&lt;Key&gt;Up: 	string(&quot;up\n&quot;) 				\n\
    None&lt;Key&gt;Left: 	string(&quot;where\n&quot;)

<pre style="background: transparent; box-shadow: none; border: none;">
Hi Mike,

&gt; 	This comes up every now and then and it might be interesting to
&gt; start a more general discussion of what features the user community would
&gt; *really* like to see in IRAF

- Command-line editing that really works (I use NCL, and it is robust;
  the xterm keymap idea, while ingenious, is a kludge that (1) isn&#x27;t
  bullet-proof, and (2) less than 0.1% of users would bother to
  install).

- Consistent reliable handling of CNTL-C interruption of scripts.

- The removal of the need to type &quot;flpr; flpr&quot; at mysterious times for
  mysterious purposes.

- Error handling. This is the biggest problem with IRAF, in my opinion.
  We need a status return codes on all scripts, and all operating system
  processes.

- Improved error messages for IRAF scripts.

- Installation via an RPM rather than an interactive shell script.

- The IRAF parameter system has a number of problems, e.g.,

     - it makes it difficult to have multiple simultaneously running
       scripts under the same username, since the parameter files clash
       (I use a temporary directory to get around this).

     - new releases often add new parameters, which can then cause
       inconsistent behaviour in existing scripts (unless you are
       careful to &quot;unlearn&quot; every program you use).

- SPP was a good idea at the time (when FORTRAN-IV was the only standard
  you could depend on), but it is now a liability, primarily because it
  is usually not a good career move for programmers to become proficient
  in it. The GNU C compiler is widespread enough to be a good substitute.

- I think the time has come to drop the cl and move to a good scripting
  language such as python or perl. The PyRAF project is on the right track
  here.

OK, that&#x27;s probably enough to go on with! I have an affection for IRAF,
and it would be nice to see it continue to be used for the next several
decades, but if it is to prosper and grow I suspect that some big
decisions will have to be made soon, and some long-held ideas abandoned.

<pre style="background: transparent; box-shadow: none; border: none;">
Hi,

First, let me say that I use IRAF a lot and I think it has a lot of
things going for it.  Thanks for a very useful software package.

But since you asked...

&gt; &gt; 	This comes up every now and then and it might be interesting to
&gt; &gt; start a more general discussion of what features the user community would
&gt; &gt; *really* like to see in IRAF
&gt; 
&gt; - Command-line editing that really works (I use NCL, and it is robust;
&gt;   the xterm keymap idea, while ingenious, is a kludge that (1) isn&#x27;t
&gt;   bullet-proof, and (2) less than 0.1% of users would bother to
&gt;   install).

I&#x27;ll second this (both the need for it and the unacceptability of the
keymap workaround).  I teach a lot of people how to use IRAF (we have
only undergraduate students here), and just the lack of a
straightforward way to type and edit commands is a big stumbling block
for people in becoming comfortable with IRAF.  In addition to
command-line recall, I&#x27;ll note a few other, related things:

* While ehistory allows one to recall and edit previous commands, it
is not easy to edit the *current* command one is typing (e.g. to arrow
back and insert a letter you missed typing).

* The behavior of the backspace and delete keys is different in
ehistory than it is in editing the current command.  If one wants to
erase the character to the left of the cursor, it&#x27;s a different key in
the current command that it is when in ehistory mode.  This is quite
confusing.  (At least this is the way it is in the default keymapping
with many computers I&#x27;ve used.)

* Parameter editing suffers from some of the same difficulties as
command line editing; no easy way to fix what you&#x27;ve typed, etc.

* The xiraf script by Vassilis Charmandaris
(http://astrosun.tn.cornell.edu/staff/vassilis/xiraf/) is a great
service to the IRAF community, but there&#x27;s no reason (that I can see)
that these things shouldn&#x27;t just be built into IRAF itself.  For
example, I can&#x27;t think of another program that won&#x27;t even look in a
*default* location (i.e. ~/iraf/login.cl) to find its startup file.
And is there a good reason not to name the default binary &quot;iraf&quot;, or
at least to have a symlink from cl to iraf?

There are a lot of great things about IRAF - but some of these little
things would make using it (and especially *learning* to use it) quite
a bit easier.

Thanks for listening,

Eric

P.S. Is ncl no longer being distributed/maintained?  I couldn&#x27;t find
it on the SAORD pages.  I&#x27;ll have to try pyraf.
</pre>
