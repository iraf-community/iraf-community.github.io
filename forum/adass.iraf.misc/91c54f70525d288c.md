# Passing pointer problems

**Roberto Abraham at IoA, Cambridge** wrote on Aug 18, 1998

<pre style="background: transparent; box-shadow: none; border: none;">
Hi -

I&#x27;m having some trouble passing a bunch of pointers to arrays from an
SPP subroutine to an SPP task, and I think I must be misunderstanding
something fundamental with regard to how pointers are passed in SPP
programs. Can anyone enlighten me?

In a nutshell, what I&#x27;m trying to do is pass a string to a subroutine,
which then finds all rows in an STSDAS table where a particular column
matches the string. I then extract a bunch of arrays from the table
and pass back pointers to these arrays. For example, say I have a
bunch of rows in the table with the string &quot;B-V&quot;, &quot;V-I&quot;, etc in one of
the columns. I call a subroutine to find the rows where that column
has &quot;B-V&quot; then return all the corresponding values in several other
columns as a bunch of arrays.

It sounds pretty trivial, and indeed my code seems to almost work.
The maddening thing is that my subroutine works fine the first time my
task calls it, but on subsequent calls the subroutine passes back
pointers to garbage instead of pointers to my arrays of numbers.  More
specifically, even after the first call the subroutine seems to be
doing the right thing internally, since *inside* the subroutine the
arrays are extracted correctly from the STSDAS table and are properly
defined when pointers to them are dereferenced, but once I pass the
pointers back to the main routine they no longer have the same target
as inside the subroutine. It looks to me that somehow I&#x27;m managing to
to deallocate the memory accidentally (or else retargeting the pointer
to hyperspace) simply by the act of passing the pointer back to the
main routine, but after staring at the code for ages I don&#x27;t see how
that&#x27;s possible.

I&#x27;m going berserk trying to figure out what the heck is happening.
Does the behaviour I describe sound like a familiar and obvious
problem to somebody... in case it is an obvious thing and you want to
laugh out loud, I&#x27;ve attatched a copy of the source below, along with
a test run, which shows how it seems to work fine the first time, and
then continues to do the right thing INSIDE the subroutine for
subequent calls, but then the pointer targets vanish when they&#x27;re
passed.

Any ideas?

# MODEL_INFO -- returns arrays giving the column numbers
# corresponding to models of a given colour, along with arrays 
# holding the corresponding column names and values of tau and E(B-V).
#####################################################################
procedure model_info (ktp, colour, tau, ebv, name, nmodel)

pointer ktp
char colour[SZ_COLNAME]
pointer tau
pointer ebv
pointer name
int nmodel

char rowcolour[SZ_COLNAME]
pointer colour_cp
pointer tau_cp
pointer ebv_cp
pointer name_cp
int i,j

int tbpsta()
bool streq()

begin
	
	call printf(&quot;Inside the model_info() subroutine... \n&quot;);
	
	call tbcfnd (ktp, &quot;Colour&quot;, colour_cp, 1)
	call tbcfnd (ktp, &quot;Tau&quot;, tau_cp, 1)
	call tbcfnd (ktp, &quot;E(B-V)&quot;, ebv_cp, 1)
	call tbcfnd (ktp, &quot;Column_Label&quot;, name_cp, 1)		
	
	if (colour_cp == NULL || tau_cp == NULL || ebv_cp == NULL ) {
	    call tbtclo (ktp) 
	    call error (1, &quot;a required column was not found&quot;) 
	}	
	
	# allocate maximum amount of memory we could possibly need. This is
	# actually a bit wasteful -- I really only need nmodel/ncolour elements.
	nmodel = tbpsta (ktp, TBL_NROWS)
	call malloc(tau,nmodel,TY_REAL)
	call malloc(ebv,nmodel,TY_REAL)
	call calloc(name,nmodel*SZ_COLNAME,TY_CHAR)
	
	j=0
	for(i=0; i&lt;nmodel; i=i+1){
	    call tbegtt(ktp,colour_cp,i+1,rowcolour,SZ_FNAME)
	    
	    if (streq(rowcolour,colour)){
		
	       	call tbegtr(ktp,tau_cp,i+1,Memr[tau+i])
	       	call tbegtr(ktp,ebv_cp,i+1,Memr[ebv+i])
	        call tbegtt(ktp,name_cp,i+1,Memc[name + SZ_COLNAME*i],SZ_COLNAME)
	       	j = j+1
		
		# Print out the variables as seen *inside* the procedure
		call printf(&quot;tau: %g   ebv: %g name: %g \n&quot;)
		call pargr(Memr[tau+i])
		call pargr(Memr[ebv+i])
		call pargstr(Memc[name+SZ_COLNAME*i])	    
		
	    }
	}
	nmodel = j
	call printf(&quot;Looks ok. I&#x27;m now leaving the the model_info() subroutine... \n&quot;);
	
end

**Mike Fitzpatrick** wrote on Aug 18, 1998

<pre style="background: transparent; box-shadow: none; border: none;">
Bob,
	The problem is that in your model_info routine you&#x27;re populating
the arrays based on the number of models in the whole table, not just the
ones matching the current color.  So, when you make the first pass it just
so happens that rows 1-4 match what you want and in the main routine you
print the first four elements.  On the second pass the subroutine fills
array elements 5-8 but you&#x27;re still printing 1-4.  The error is in the use
of &#x27;i&#x27; and &#x27;j&#x27; in the subroutine, and the way you&#x27;re incrementing &#x27;j&#x27;.
Try instead (I&#x27;ve indicated the lines needing changes):

    j=0
    for(i=0; i&lt;nmodel; i=i+1){
        call tbegtt(ktp,colour_cp,i+1,rowcolour,SZ_FNAME)
        
        if (streq(rowcolour,colour)){
            call tbegtr(ktp,tau_cp,i+1,Memr[tau+j])		 # &lt;----
            call tbegtr(ktp,ebv_cp,i+1,Memr[ebv+j])		 # &lt;----
            call tbegtt(ktp,name_cp,i+1,Memc[name+SZ_COLNAME*j], # &lt;----
		SZ_COLNAME)

            # Print out the variables as seen *inside* the procedure
            call printf(&quot;tau: %g   ebv: %g name: %g \n&quot;)
                call pargr(Memr[tau+j])				  # &lt;---
                call pargr(Memr[ebv+j])				  # &lt;---
                call pargstr(Memc[name+SZ_COLNAME*j])		  # &lt;---
            j = j+1				  		  # &lt;---
        }
    }
