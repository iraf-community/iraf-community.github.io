# ERROR: FXF: syntax error in kernel section \[solved\]

**Nicola Caon** wrote on Jun 26, 2009

{% raw %}
<div>
Hi,<br>
<br>
I was helping a user who was using mscred.ccdproc to process some multiextension fits files produced by a new instrument at the GTC (mscred v4.9 under Iraf v2.14.1 on a Fedora 8 PC).  <br>
The problem showed up when he tried to subtract out an averaged bias from a flat field image.<br>
The same error message though is displayed when using ccdlist.<br>
<br>
<pre><code>mscred&gt; ccdlist flat_i.fits 
ERROR: FXF: syntax error in kernel section
  &quot;ccdproc=&quot;&quot;)&quot;
     line 18: mscsrc$ccdlist.cl
     called as: `ccdlist (images=flat_i.fits)&#x27;
</code></pre><br>
<br>
After inspecting the header of all extensions looking for obviously malformed keywords, and checking the source code of the ccdlist task, I found that the problem was caused by the dashes in the string value of the EXTNAME keyword.<br>
<br>
<pre><code>mscred&gt; hedit flat_i.fits[1] EXTNAME .
flat_i.fits[1],EXTNAME = CCD-1-L1</code></pre><br>
<br>
The solution was simply to use hedit to replace the dashes with underscores (CCD-1-L1 --&gt; CCD_1_L1, etc.) .<br>
<br>
Is this a (very understandable and reasonable) limitation of mscred in handling ETXNAME values, or does using dashes in the EXTNAME value violate the FITS standards?<br>
<br>
And should I tell the instrument team about this, so that they can correct the software that writes the FITS header?     <br>
<br>
Thanks very much<br>
Nicola
</div>
{% endraw %}

**Mike Fitzpatrick** wrote on Jun 26, 2009

{% raw %}
<div>
Hi Nicola,<br>
<br>
Thanks for identifying the problem so clearly.  The '-' isn't explicitly forbidden by the FITS standard for values as far as I know, nor is it explicitly excluded by the FITS kernel in IRAF.  However, the way the kernel section is being parsed by the FITS kernel, the '-' is being confused with the use of a hyphen to mean turn off a parameter (e.g. "inherit-" instead of "inherit=no").  <br>
<br>
Because the hyphen is in the value, I think it's actually a bug in the fits kernel parser code.  Fixing this would require some investigation and then a completely new set of binaries, or at least a new library you have to install and then relink external packages in order to have effect.  For now, the simplest fix of editing the value may be the best.  The instrument team might well be willing to change the field, assuming of course doing so wouldn't break any other software.<br>
<br>
-Mike
</div>

**Francisco Valdes** wrote on Jun 26, 2009

<div>
I might also add that using quotes or \ escapes would allow extension names with characters also used by the FITS kernel syntax.  But for something like ccdproc or other mscred-type scripts the script code would probably need a fair amount of massaging and not worth the effort.<br>
<br>
I would also mention another drawback of the FITS kernel syntax.  An extension name cannot be a number because something like<br>
<br>
<pre><code> abc.fits[4]</code></pre><br>
<br>
Assumes the number is the position in the file.  In other words, in order to allow both an order number and an extension name in the syntax (filename[order][extname,...]) the parser has to make some assumptions.<br>
<br>
So, while the extension names are allowed to be anything, there are some limitations for making data work efficiently in reductions.  It's like saying your could have a 68 character extension name but a user reducing data would not want to have to type out such a thing.<br>
<br>
My thoughts,<br>
Frank Valdes
</div>
