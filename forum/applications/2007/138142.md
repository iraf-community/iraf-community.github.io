Michael,<br>
<br>
Frank may comment further, but I think part of the answer is in an earlier reply of his:<br>
<br>
<blockquote>It can confuse programs when the image type changes.  CCDPROC typically<br>
works "in-place", meaning a temporary image holds the processed image<br>
until successful completion and then it replaces the input image.<br>
Because you must have the "imtype" environment variable set to "fits"<br>
it creates a fits a temporary fits output.  The replacement is simply<br>
a move so the image type is not changed back to imh.  If you have specified<br>
the input as something like *.imh, the next time it wants to access the<br>
image it looks for a imh which it doesn't find because now it is fits.<br>
This would typically happen when a dependent calibration image is processed<br>
automatically before applying to the data.<br>
<br>
In short, CCDPROC does not like to work with input in one format and<br>
"imtype" set to a different type.  The solution is to either reset<br>
you input to fits or, easier, "reset imtype=imh" followed by flpr.<br>
In the latter situation everything will be done in imh as you probably<br>
have done before.<br>
</blockquote><br>
<br>
In your case you need to check not only your setting of 'imtype' (used to set the default type of new images if no extension is given explicitly), but also that the 'imextn' allows ".fts" as a valid extension (do a 'show imextn" to check).  The problem may also be that  in part that the '.fts' extension is being mangled to a ".fits" extension in the processing as described above.  You can change all the .fts extensions to .fits using a command such as <br>
<br>
<pre><code>cl&gt; rename *.fts fits field=extn</code></pre><br>
<br>
Hope this helps.<br>
<br>
Cheers,<br>
-Mike
