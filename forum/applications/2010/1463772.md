Below is a script you can use to calculate the exact area of a polygon, for the vertices you list I get a different number still, 123.8726.<br>
<br>
The thing to remember is that the area used by POLYPHOT is just an approximation based on some estimate of the overlap of the polygon with a particular pixel (which is used to compute the fraction of flux contributed by that pixel).  I believe (but haven't verified) that this is done in pixel space so the fraction computed will be the same regardless of the plate scale.  Although the POLYPHOT value is higher, I'm not sure this approximation is what could be called a bug.  Unfortunately the programmer who wrote the task is no longer with us so it will take some digging to get into the algorithm to understand if it really is a problem, or what might be done to improve the value.<br>
<br>
Cheers,<br>
-Mike<br>
<br>
<pre><code>
#{  POLYAREA -- Compute the area of a polygon given an input list of 
#   vertex points.
#
#   Usage:    cl&gt;  task $polyarea = /path/polyarea.cl
#             cl&gt;  polyarea &lt; vertex.txt
#
#   Where &#x27;vertext.txt&#x27; is a text file containing one (x,y) vertext point
#   per line.

procedure polyarea ()

begin
    real  a, b, c, d, sum

    sum = 0.0
    j = scan (a, b)
	
    i = 1
    while (scan (c, d) != EOF) {
	sum = sum + (a * d - c * b)
	a = c
	b = d
	i = i + 1
    }

    printf (&quot;Area = %.5f   Nvertices = %d\n&quot;, abs(sum / 2.0), i)
end
