**Mike Fitzpatrick** wrote on May 09, 2012

{% raw %}
<div>
Thanks for the post, it gives me a few ideas:  I don't think it's specifically a mixed-architecture problem, the CL will happily use a package's 32-bit binary when using a core 64-bit architecture.  However, the CL in this case is still the 64-bit version and is responsible for providing the graphics kernel to render the plot.  There've been issues in the past where graphics metacode was found to be incompatible due to changes in the size of an INT, and this may be a case where the 32-bit-generated metacode isn't being handled properly by the 64-bit CL.<br>
<br>
To isolate this, you could try running a 32-bit CL explicitly, i.e. invoke the $iraf/bin.linux/ecl.e from the commandline to start a CL (or else temporarily swap the normal $iraf/bin.linux64/ecl.e with the 32-bit version and start normally).  If you use a 32-bit CL and ELLIPSE works then either the CL has a bug or the ELLIPSE task is doing something not seen elsewhere to set the window boundaries.  It would also help to know the date of the CL binary you are using, or else do a "make latest" from the $iraf directory to be sure you're running the latest update.<br>
<br>
If you get a plot, could you do a ":.write &lt;file&gt;" and ":.gflush" to save the metacode to "&lt;file&gt;" and post that to the anonftp at <a href="ftp://iraf.noao.edu/pub">ftp://iraf.noao.edu/pub</a> so I can try to reproduce the problem here?  OTOH, if you see the same problem then it may be an issue for STScI to take up.
</div>
{% endraw %}
